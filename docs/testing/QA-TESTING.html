ActualTime 5.0.0 — QA testing

Target: GLPI 12.0.x. Run once on a clean install and once on an upgrade from ActualTime 4.x with existing timers.

Result: write OK or KO only. Comments: for a KO, the error message, a screenshot reference or what went wrong.

Users needed: a Super-Admin; two technicians (Technician profile), Tech A in the root entity (recursive) and Tech B in a child entity Entity B only; a Self-Service user. Give the Technician profile the ActualTime rights (Administration › Profiles › Technician › ActualTime tab: running timers + all four task types).

Markers: the plugin only writes into GLPI's own database. Ordinary rows change test data (timers, tasks); rows in the last section are [destructive] and must be run deliberately, last. Sections marked (optional) apply only if that plugin is installed; skip them as a whole otherwise.

1. Installation and settings

#CheckStepsExpectedResultComments
1.1Install and enableSetup › Plugins: install, then enable ActualTime.Both succeed with no error message. Status "Enabled".
1.2Upgrade keeps dataUpgrade case only: before upgrading, note the timers of a 4.x task. Upgrade, enable, open the task.The same segments and total time are shown.

1.6Settings need config rightsAs Tech A, try to open Setup › General.No access to the ActualTime settings.

Known limitations

  • Timer events in the planning are not draggable: a timer segment is a time record, corrected from the task's "Modify timers" window (since 5.0.0).
  • The generic list /plugins/actualtime/front/task.php is always empty: it is not a plugin feature and is closed for security; the ActualTime columns of the ticket and task lists keep working.
  • Hiding private tasks (5.7) depends on the "See private tasks" right: the stock Technician and Super-Admin profiles of GLPI 12 have it, so for them nothing changes.
  • Reports (actualtime totals per user) need the Reports plugin; without it those pages return "not found".
